## データソース

町丁目の境界・統計データは、本番アプリ（町丁パズル等）と同じCloudFront配信のGeoJSONを直接fetchしている（`stat.usapo.net`のKMZではない。本体側の`docs/sample/`配下の古いプロトタイプはKMZ経由だが、現行のCloudFront配信は変換済みの素のGeoJSON）。

- 都道府県: `{CLOUDFRONT_URL}/geojson/prefecture/prefectures.geojson`
- 市区町村: `{CLOUDFRONT_URL}/geojson/municipality/2020/{prefCode}.geojson`
- 町丁目: `{CLOUDFRONT_URL}/geojson/town-district/2020/{prefCode}/{cityCode}.geojson`
  - プロパティ: `KEY_CODE` / `PREF_NAME` / `CITY_NAME` / `S_NAME` / `AREA`(m²) / `SETAI`(世帯数) / `JINKO`(人口)

`CLOUDFRONT_URL` は本体側の`.env.local`に2系統ある（開発 `db5yov8jlk17b` / 本番 `dbr7d89af0fox`）。モック内の「詳細設定」からどちらでも切り替えて試せる。**本番CloudFrontはこのHTMLを開くオリジンがS3バケットのCORS `AllowedOrigins` に入っていないと直接fetchに失敗する**（新ドメインからの直接fetchを追加する場合はS3バケット側のCORS設定に手動追加が必要。このS3バケットは本体側のAWSアカウントが管理している）。失敗した場合はCORSエラーである旨をステータス欄に表示する。

## 属性スコアの算出式（暫定・要調整）

設計書の判定条件をそのままスコア化した「複合スコア方式」。町丁目ごとに以下4つのスコアを計算し、最大のものをその町丁目の属性とする。

正規化は市区町村内でのパーセンタイル順位（0〜1）を使用（外れ値に強い min-max の代替）。

- `areaNorm`: 面積（`AREA`）の順位
- `densityNorm`: 人口密度（`JINKO / AREA`）の順位
- `compactNorm`: コンパクト比（Polsby–Popper指数 `4π×面積 / 周囲長²`。周囲長はポリゴン外周をhaversine距離で近似）の順位
- `avgHouseholdNorm`: 世帯当たり人数（`JINKO / SETAI`）の順位（持ち家率データは未取得のため代理指標として世帯人数のみ使用）

```
地(land)  = areaNorm × (1 − densityNorm)
火(fire)  = areaNorm × compactNorm
風(wind)  = (1 − areaNorm) × densityNorm
水(water) = (1 − |areaNorm − 0.5| × 2) × avgHouseholdNorm   // "中程度の面積"がピークになる山型
```

この式はバランス調整前の仮置き。実データで4属性の分布に極端な偏りが出るようなら重み・式を調整する。

### 更新: 空港・田園調布(大田区)を見て調整(2026-07-16)

大田区で見ると、羽田空港（人口ゼロ・巨大面積）と田園調布（世帯当たり人数トップクラスの高級住宅地だが区画は広め）がどちらも「地」判定になってしまう問題があった。原因は「地」の式が"面積大・密度低"しか見ておらず、そこに実際どれだけ人が住んでいるか（人口の絶対量）を見ていなかったこと。以下の2点を修正:

```
地 = areaNorm × (1 − densityNorm) × (1 − jinkoNorm)   ← 人口の少なさそのものを追加で要求
水 = (1 − (|areaNorm − 0.5| × 2)²) × avgHouseholdNorm  ← 「中程度の面積」ペナルティを直線→二乗にして緩和
```

大田区で試した結果、田園調布7町丁目のうち「田園調布南」だけが水属性に変化（守備力2462、人口3803）。残り6町丁目（本町・一〜五丁目）は地/火のままで、地との僅差（例: 五丁目は地0.418 vs 水0.305）ではあるものの、水が優勢になったのは1つだけだった（2026-07-16に一度「3町丁目」と記載したが、これは式を最終調整する前の中間結果の記録ミス。2026-07-21に実データで再検証して訂正）。羽田空港は人口ゼロのため引き続き地属性のまま——これは意図した挙動というより、**4属性モデルに「インフラ・空港」を表現する枠自体が無いという設計上の限界**。無理に名前パターンでごまかさず、正直に残している（詳しくは下記「既知の限界」参照）。

### 既知の限界

- 空港・港湾施設のような大規模インフラは、人口ゼロ・面積大という点で自然の森林と統計的に区別がつかない。4属性(火水地風)だけでは表現しきれておらず、5つ目の属性を作るか、諦めて「地」寄りの扱いにするかは今後の検討事項。

### 方針転換: 実世界ラベルを外す（2026-07-16）

檜原村（町丁目数13という小さな自治体）で確認すると、山間の集落ばかりなのに「火属性が多い土地」になる現象があった。原因は `percentileRanks`（市区町村内での相対順位による正規化）の限界で、大田区のように町丁目数が多く土地の性質が多様な区では機能するが、檜原村のように内部がほぼ均質な自治体だと「その自治体の中で一番○○」というだけで無理に4属性へ引き伸ばされてしまい、実態と乖離する。

正規化の精度を追い込む方向（絶対値ベースの尺度に置き換える等）も検討したが、**「地＝森・農地」「火＝工業地帯」のような実世界ラベル・判定条件の説明文自体を外す**方針にした。属性はあくまで統計的に算出された相対的な区分であり、ゲームプレイ上意味を持てば十分（属性一致ボーナスで戦略が生まれる）で、実際の土地利用を言い当てることを目指さない、という整理。`attribute-map-mock.html`の凡例からは「森・農地」等の説明文を削除し、単に「地属性」とだけ表示するようにした（`battle-phase-mock.html` / `integrated-loop-mock.html` の凡例も同様）。

## 隣接判定について（movement-phase-mock.html）

町丁目境界データにトポロジー情報（どの町丁目とどの町丁目が隣接するか）は含まれていないため、モック内でポリゴンの頂点間近接度から簡易的に推定している。バウンディングボックスが重なる候補ペアのみ、頂点間の距離（メートル換算、閾値40m）で判定する近似実装。境界データがトポロジー上ほぼ頂点共有されているため実用上は機能するが、本実装では要検証・要改善（境界線の共有判定など、より厳密な手法に置き換える余地あり）。

## 検証済み: 羽田空港二丁目↔多摩川河川敷（下流）の隣接は正しい

大田区で「羽田空港三丁目→（強制1択で）羽田空港二丁目→多摩川河川敷（下流）」という2ホップ移動が起き、一見「ワープ」しているように見えたため調査した。

結果、**隣接判定のバグではなく実際に隣接している**ことを確認した。羽田空港二丁目のポリゴンリング上の連続3頂点 `[16][17][18]` が、多摩川河川敷（下流）側のリング `[85][84][83]`（逆順）と座標レベルで完全一致（距離0.00m）しており、これは2つのポリゴンが同じ境界線を反対周りにたどっている典型的なパターン。地理的にも羽田空港は多摩川河口に位置しているため、隣接は妥当。対応不要、現状のまま（`HCODE === "8154"` の水面除外のみ）とする。

ただし、多摩川河川敷（下流）自体は2.4km²・377頂点という他の町丁目（多くは数万〜数十万m²程度）よりかなり大きい地物であるため、こういった大きな地物を他の町丁目と同格の「1マス」として扱ってよいか（重心へのワープ演出が大きな地物では違和感になりうるか）は、今後別の地域でも同様の見た目になった際に改めて検討する。

## 戦闘フェーズの暫定計算式（battle-phase-mock.html・要調整）

設計書で「未確定」とされている守備側基礎値・攻撃側パワーの計算式を、このモックでは以下のように仮置きしている。

```
守備力 = max(20, round((人口×0.6 + 面積(ha)×8) × 属性別維持コスト係数))
  属性別維持コスト係数: 火=1.3 / 風=1.5 / 水=1.0 / 地=0.5

攻撃力 = デッキ5枚の合計（カード属性が土地属性と一致する場合、そのカードのみ+25%）

事前勝率 = clamp(攻撃力 / (攻撃力 + 守備力), 5%〜95%)
サイコロ補正 = (出目1〜6 − 3.5) × 6%
最終勝率 = clamp(事前勝率 + サイコロ補正, 5%〜95%)
```

カードは本来は攻略した土地の特性に応じて入手する想定（設計書「カードシステム」）。本モックでは獲得ロジックまでは実装せず、初期所持を無属性4種＋地属性1種の5枚に固定し（地属性＝難易度カーブ上いちばん易しい属性という想定）、残り7枚は🔒未所持としてロック表示のみ行う。デッキはいつでも自由に組み替えてよい（挑戦する町丁目ごとに固定し直す必要はない）。属性の相性は「同属性なら+25%」のみで、火→風→地→水のような三すくみ相性は設けない（カルドセプト本家に準拠）。

## カード獲得トリガーについて（card-acquisition-mock.html）

属性カードは `HCODE=8154`(水面)除外後の町丁目の算出属性からそのまま付与するので構造的に妥当だが、**アクセス系カード（離島/フェリー/空港）の付与条件は町丁目名の文字列パターン（「島」「港」「空港」）による、このモック限定の簡易判定**。movement-phase-mockの隣接判定で「地物名の文字列パターンマッチには頼らない」と決めた方針とは別枠——あちらは実際の地理的隣接関係というゲームロジックの正しさに関わる判定だったのに対し、こちらは「カード獲得演出を試すためのトリガー」というUI検証の便宜上の仮実装のため、実装での本采用時は国土数値情報の空港・港湾・離島データ等、構造化されたデータソースに置き換える前提。

## 占領地の二層構造の暫定パラメータ（occupation-investment-mock.html・要調整）

```
実効守備力 = 基礎守備力 ×(1 + 投資ボーナス)
投資する: ボーナス += 15%/ターン（上限 +150%）、維持費として 基礎守備力×5%/ターン を資金から消費
放置する: ボーナス -= 8%/ターン（下限 0% = 基礎値に戻る）
維持費を全額払えないターンは、投資中だった町丁目も含めて全て減衰扱いになる

収入（設計書「インフラ経済システム」由来、占領していれば投資中/放置中問わず毎ターン発生）:
  収入 = 基礎守備力 × 属性別収入率
  属性別収入率: 火=8% / 風=9%（通行料主力・本モックには競合プレイヤーがいないため取りこぼしは考慮せず） / 水=5% / 地=3%（低収入・安全資産）
```

増減率・維持費率・収入率は仮の値。プレイスタイル（拡張型=広く浅く投資せず数で稼ぐ／拠点型=少数に集中投資／ハイブリッド型）の分岐がバランスとして機能しているかは未検証。単体では「維持費だけ発生して資金がジリ貧になる」だけの片手落ちな作りだったが、収入を足したことで収支のバランス感を検証できるようになった（2026-07-16に追加）。

## 市区町村マクロ構造について（macro-structure-mock.html）

市区町村単位の守備力は、その市区町村に属する全町丁目データを集計（人口合計・面積合計）して算出している。都道府県全体（最大62市区町村）の町丁目データを並行取得するため、読み込みに数秒〜十数秒かかる。devバケットで町丁目データが全市区町村分揃っているのは東京都(13)のみなので、他県は市区町村レベルの隣接ロックは動くが守備力が0扱いになる区市町村が出る。

侵入口の動的決定は、直前にいた市区町村と新たに占領する市区町村、それぞれの町丁目データ全件同士でバウンディングボックス絞り込み＋頂点近接判定を行い、実際に境界を接するペアを探す実装。大田区(220町丁目)×世田谷区(277町丁目)の組み合わせでも実測65ms程度で、ブラウザ上のクリック操作としては十分な速度。

複数の占領済み隣接自治体から攻め込める場合は「どちらから来たか」を選択させ、選んだ経路によって侵入口（=最初に立つ町丁目）が変わる。これが「実際に歩いてきたルートが反映される」という設計書の意図の実装。

## 観光要素の暫定パラメータ（tourism-mock.html・要調整）

```
観光地ONの場合のみ、季節倍率が収入全体にかかる: 春×1.0 / 夏×1.6 / 秋×1.2 / 冬×0.7
観光地OFFなら季節の影響を受けない（通常収入のまま）
「次のターンへ」を押すたびに季節が1つ進む（春→夏→秋→冬→春…）
```

観光地フラグは設計書どおり市区町村単位で一括適用（町丁目ごとの判定はしない）。判定方法・季節倍率とも実データ（観光統計・インバウンド動向）とは未連動で、設計書が言う「まずは固定の季節倍率から始める」という段階的実装そのままの状態。

## 移動手段の進化について（movement-cards-mock.html）

離島/フェリー/空港の3カードは、いずれも町丁目名の文字列パターン＋距離条件（離島=「島」を含み8km以内、フェリー=「港」を含み5km以内、空港=「空港」を含み距離無制限）で判定する、このモック限定の簡易実装。実装時は国土数値情報の橋梁・港湾・空港・離島データに置き換える前提（card-acquisition-mockのアクセス系カード判定と同じ位置づけ）。

「港」のパターンが「空港」にも誤ヒットする問題があったため、`/(?<!空)港/`という否定後読みで除外している（東京都・大田区の羽田空港エリアで実データ検証済み）。

## 他プレイヤーの占領地の暫定パラメータ（rival-territory-mock.html・要調整）

```
CPU縄張りの割当: 全町丁目のうち約20%をランダムに割当、守備力は投資済み想定で×1.3
通行料 = CPU territoryの守備力×10%（払うと資金だけ減り、現状維持のまま先に進める）
奪還戦闘: battle-phase-mockと同じデッキ・勝率計算式。守備力はCPUの+30%込みの値を使う
```

CPUの縄張りはランダム割当のみで、実際に他プレイヤーが行動する仕組みは無い（あくまで「固定された障害物」としてのシングルプレイ検証）。

## マクロ⇄ミクロ統合について（macro-micro-integrated-mock.html）

macro-structure-mock（市区町村単位の攻略・隣接ロック・動的侵入口）と integrated-loop-mock（サイコロ移動＋戦闘のワンループ）を1つのHTMLに統合した、このフォルダの中で最も作り込んだモック。

- 市区町村をクリックすると、直前にいた区市町村との境界を接する町丁目ペアを探索して侵入口を動的決定 → その侵入口を開始位置として、その区市町村の町丁目レベルのミクロ画面（属性色分け・サイコロ移動・遭遇戦闘）に切り替わる
- ミクロ画面で「▶ マクロ画面に戻る」を押すと、その時点で区市町村を確保（マクロ層で occupied 扱い）し、隣接する次の区市町村が解放される。**町丁目を100%制覇していなくても、途中で戻れば確保扱いになる簡略化**をしている（設計書に完全制覇の要件は明記されていないため、モックとしてはこの簡略化で十分と判断）
- デッキ・資金・ターン数はマクロ/ミクロ両層で共有（区市町村をまたいでも維持される）
- 既に確保済みの区市町村（開始拠点を含む）も再クリックでミクロ画面に戻れる。町丁目レベルの占領状態は区市町村ごとに保持される
- 都道府県全体（最大62市区町村）の町丁目データを事前に並行取得するため、初回読み込みに時間がかかる（macro-structure-mockと同様）
