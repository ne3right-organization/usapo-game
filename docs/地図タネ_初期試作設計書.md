# 地図タネ 初期試作設計書

**バージョン：0.3 ／ 2026-10-28**

## 0. この文書について

- [全体設計書](地図タネ_全体設計書.md)のうち、最初に作る試作の範囲と作り方をまとめたもの。ゲームのルールや用語は全体設計書に従う
- 0.1 は ChatGPT との壁打ちで作った「箱庭の表示・配置・保存」だけの試作だった（本文は壁打ちの会話にある）。全体設計が固まったのに合わせて作り直し（0.2）、ゲーム名などが決まったのに合わせて直した（0.3）

## 1. 試作で確かめること

**「現地に行って、他の人の拠点からもらう」が楽しいか。** メインは拠点を訪ねることで、箱庭はおまけ（全体設計書 1章）。

このゲームならではの部分は「現地でもらう」ところにある。成長・ランクアップ・レベルは入れずに、「拠点を置く → 他の人の拠点を訪ねてもらう → 集めたものを見る・飾る」の一周を最小限の形で通し、dev 環境（devgame.usapo.net）で実際に街を歩いて試す。

確かめたい問い（大事な順）:

1. 地区に拠点を置き、別の地区で他の人の拠点にチェックインする、という流れが分かりやすいか。「他の人の拠点に行ってみたい」と思えるか
2. ブラウザの位置情報で、地区の判定が実用になるか（誤差、境界付近、スマホでの許可の出し方）
3. もらったものを集めて眺める・箱庭に飾るのが、ご褒美としてうれしいか
4. スマホで操作しやすいか

絵柄（全体設計書 10章の「一番の難所」）は、コードとは別に並行して確かめる（10章）。

## 2. 範囲

### 作るもの

| 機能 | 内容 |
|---|---|
| コース選び | 初めて開いたときに5つから選ぶ |
| いまいる地区 | 位置情報から地区を判定して、地名とその市区町村の地図（拠点のある地区に印）を出す |
| 拠点を置く | いまいる地区に拠点が無ければ置ける（1地区1つ・早い者勝ち）。種類は自分のコースの1種類目 |
| チェックイン | いまいる地区に他の人の拠点があれば、チェックインしてもらう（拠点ごとに1日1回） |
| 集めたもの | 持っているものの一覧。どこでもらったか（地名）も出す |
| 箱庭（おまけ） | 持っているものを、所持数まで置く・動かす・しまう。保存して次回も同じ状態で出す |
| 開発用の位置指定 | dev 環境と手元だけ、地図をタップして「いまいる場所」を指定できる（9章） |

### 作らないもの（全体設計書の後のフェーズ）

- 拠点の成長・ランクアップ・収穫・季節（拠点はランク1のまま）
- プレイヤーレベルと、2種類目・3種類目の拠点
- タネ・合成・交換
- 他の人の箱庭を見る
- 未ログインでの利用（試作はログイン必須）

## 3. 一周の流れ

```
 初めて開く ─→ コースを選ぶ(例: 乗り物) ─→ 自転車 ×3 を持った状態で始まる
                                            │
 ┌──────────────────────────────────────────┘
 ▼
「いまいる地区」を開く ─→ 位置情報で地区を判定(例: ○○町)
 │
 ├─ この地区にタネが無い ─→ [タネをまく] ─→ ○○町にサイクルポートができる
 │
 ├─ 他の人のタネがある ──→ [チェックイン] ─→ その拠点のもの(例: △△町の果樹園 → みかんの木)をもらう
 │                                          (この拠点からは今日はもうもらえない)
 └─ 自分のタネがある ───→ 様子を見るだけ
 ▼
「集めたもの」で眺める ─→ (おまけ)「タネニワ」に自転車とみかんの木を並べて保存
```

## 4. ルール（試作での形）

全体設計書の決定のうち、試作に入るものと、試作だけの簡略化。

| 項目 | 試作での形 | 全体設計書 |
|---|---|---|
| コース | 5つ（植物・動物・趣味・乗り物・建物）から1つ選ぶ。あとから変えられない | 3章 |
| 拠点の種類 | 自分のコースの1種類目だけ（果樹園・小鳥の林・撮影スポット・サイクルポート・パン屋）。レベルが無いので選ばない | 3.1・3.3 |
| 拠点のランク | 常にランク1（成長しない） | 3.3・5.1 |
| もらえるもの | 拠点の種類のランク1のもの（みかんの木・すずめ・カメラ・自転車・食パン）を1つ | 3.3・6.2 |
| 最初に持つもの | 自分のコースの1種類目のランク1のもの ×3 | 3.1 |
| 拠点を置ける場所 | 1地区に1つ、早い者勝ち。1人で置ける数は制限なし（地区が違えばいくつでも） | 6.1 |
| チェックインできる場所 | 拠点のある地区の中ならどこでも | 6.2 |
| もらえる回数 | 拠点ごとに1日1回（日本時間で日付が変わったら、またもらえる） | 6.2 |
| 自分の拠点 | チェックインはできるが、もらえない | — |
| 箱庭に置ける数 | 所持数まで。1マスに1個 | 4.4 |
| 箱庭の広さ | 10×10 マス（仮） | — |
| 位置の偽装 | 直前のチェックイン（または拠点の登録）からあり得ない速さで移動していたら断る。dev では確かめない | 12章 |

使うものは5種類だけ（みかんの木・すずめ・カメラ・自転車・食パン）。違うコースのものは、他の人の拠点にチェックインしないと手に入らない。

> 1人で試すときは、Google アカウントを2つ使い、開発用の位置指定（9章）で別々の地区に拠点を置いて、お互いにチェックインする。

## 5. 画面

トップページのゲーム一覧に「地図タネ（プロトタイプ）」として載せる。スマホでの縦画面を優先する。

| 画面 | URL | 内容 |
|---|---|---|
| トップ | `/game/chizu-tane` | 初回はコース選び。2回目からは「いまいる地区」への大きな入口、自分のタネの一覧（地名・種類・Lv）、「集めたもの」「タネニワ」への入口 |
| いまいる地区 | `/game/chizu-tane/here` | 「現在地を調べる」ボタン → 地区名と、その市区町村の地図（Leaflet。タネのある地区に印、いまいる地区を強調）。下に、地区の状態に応じたボタン（タネをまく／チェックイン／自分のタネ） |
| 集めたもの | `/game/chizu-tane/collection` | 持っているものの一覧（絵・名前・数・初めてもらった地名と日付）。まだ持っていないものは影絵で出し、「どこかのタネでもらえる」ことが分かるようにする |
| タネニワ（おまけ） | `/game/chizu-tane/garden` | 斜め見下ろしのマス目（SVG）と、持っているものの一覧（残り数／所持数）。一覧で選ぶ → 空いたマスをタップで置く。置いたものをタップで選ぶ → 空いたマスで移動、「しまう」で一覧に戻す。保存ボタン。保存していない変更があるときは、画面を離れる前に確かめる |

- 位置情報の許可は、ボタンを押したときに求める（画面を開いただけでは求めない）。断られたときは、許可の出し方を案内する
- タネに出すのは、地名・種類・Lv（試作では常に Lv.1）だけ。置いた人は出さない（全体設計書 6.1）

## 6. 地区の判定

### 6.1 流れ

1. **ブラウザ**: 位置情報（緯度・経度）を取る
2. **ブラウザ**: どの市区町村にいるかを調べる（下の 6.2）
3. **ブラウザ**: その市区町村の町丁 geojson（`/geojson/town-district/2020/{prefCode}/{cityCode}.geojson`、CloudFront）を読み、点がどの町丁ポリゴンに入るかを判定して、地区名と地図を出す
4. **Lambda**: 拠点の登録・チェックインのときは、ブラウザから**緯度・経度と市区町村コード**を受け取り、Lambda 側で同じ geojson を読んで判定し直す。ブラウザが言う地区は信用しない。市区町村コードは探す範囲を絞るためだけに使い、点がその市区町村のどの町丁にも入らなければ断る

- 点がポリゴンに入るかの判定は、画面と Lambda で同じ関数を使う（`src/lib/game/chizuTane/` に置き、図鑑クイズの `zukanQuizGenerator.ts` と同じやり方で Lambda からも読む）
- Lambda は geojson を同じコンテナの中のメモリに持っておく（図鑑クイズと同じ）
- 町丁を一意に表すキーは、geojson の町丁のコード（e-Stat 小地域の `KEY_CODE` など。実装時に中身を確かめる）。拠点の主キーにする
- 誤差があるので、判定した地区を見せて「この地区で合っていますか？」と確かめてから登録する（全体設計書 6.1）。境界付近では違う地区になることがあるが、試作ではそのまま受け入れ、どのくらい困るかを確かめる

### 6.2 市区町村を調べる方法

全国の市区町村ポリゴンを読むと重いので（CLAUDE.md の「47都道府県分をまとめて取らない」）、次のどちらかにする。実装時に決める。

| 方法 | 内容 | 気になる点 |
|---|---|---|
| A. 国土地理院の逆ジオコーダ | 緯度・経度を渡すと市区町村コードと町名が返る API | 外部 API に頼る。利用条件と CORS を確かめる |
| B. 都道府県 → 市区町村の順に絞る | 都道府県の境界（`prefectures.geojson`）で都道府県を決め、その都道府県の市区町村 geojson で市区町村を決める | 読むデータが大きい（市区町村の geojson は 2MB を超える県がある） |

A が使えれば A。いずれにしても、最終的な地区の判定は町丁 geojson で行う（逆ジオコーダの町名は使わない）。

## 7. データ（Amplify Data のモデル）

既存のゲームと同じく、**モデルはクライアントからは読むだけ、書くのは Lambda だけ**にする（所持数・1日1回・早い者勝ちなどを守るため）。モデル名は `GameTane*`。

| モデル | 主キー | 中身 | クライアント |
|---|---|---|---|
| `GameTanePlayer` | `userId` | 選んだコース、直前のチェックインの地区とその代表点・日時（速さの確認用） | 本人だけ読める |
| `GameTaneBase`（拠点） | `areaKey`（町丁のキー） | 持ち主の `ownerId`、都道府県・市区町村・町丁のコードと名前、拠点の種類、ランク、開いた日時。`ownerId` で引けるようにする（自分のタネの一覧） | ログインしていれば誰でも読める（持ち主の ID は画面に出さない） |
| `GameTaneVisit`（訪問） | `userId` + `areaKey` | 最初に訪ねた日時、最後にもらった日（日本時間の日付）、訪ねた回数 | 本人だけ読める |
| `GameTaneItem`（所持） | `userId` + `itemId` | 所持数、初めて手に入れた日時と地区（集めたものの一覧に出す） | 本人だけ読める |
| `GameTaneGarden`（箱庭） | `userId` | 広さ、置いたものの配列（`objects`、`a.json()`） | 本人だけ読める |

- **位置は地区の単位でしか保存しない**。速さの確認にも、チェックインした地区の代表点（ポリゴンの中の1点）を使い、プレイヤーの実際の緯度・経度は保存しない（全体設計書 12章）
- 訪問は、のちにレベル（たずねた拠点の数）を数えるのにもそのまま使える（1拠点1行）
- 拠点の種類とランクは拠点の行に持つ（拠点に置くものは1つだけなので、全体設計書 9章の LocationObjects は分けない）
- 箱庭は1行にまとめる（保存が1回で済み、途中で失敗しても半端な状態が残らない。10×10 なら最大100個で数KB）。重なり順は奥から描けば決まるので持たない
- コースの表（拠点の種類・ランクごとのもの）とアイテムの定義はテーブルにせず、コードの中のマスターデータ（`src/lib/game/chizuTane/` の中）にする。画像を `public/` に置く以上、足すのはどのみちデプロイが要るので、「表に1行足して画像を置く」で済ませる。Lambda も同じ定義を読む。試作の段階から全体設計書 3.3 の「最初に用意する絵」の表（5コース×3種類×3ランク＝45点）を入れておき、使うのは各コースの1種類目のランク1だけにする。表の形は最初から10種類×10ランクを入れられるようにしておく

## 8. API（カスタムミューテーション）

どれもログイン必須。ユーザーIDは引数で受け取らず、Cognito の `sub` を使う。

| ミューテーション | 引数 | 処理 |
|---|---|---|
| `startTane` | コース | まだ始めていなければ、コースを決めて、最初のもの ×3 を渡し、空の箱庭を作る |
| `placeTaneBase` | 緯度・経度・市区町村コード | 地区を判定し直し、速さを確かめ、その地区に拠点が無ければ、自分のコースの1種類目の拠点をランク1で作る（同時に置こうとしたときは、DynamoDB の条件付き書き込みで先に書いた方だけが通る） |
| `checkInTaneBase` | 緯度・経度・市区町村コード | 地区を判定し直し、速さを確かめ、その地区の拠点を探す。他の人の拠点で、今日まだもらっていなければ、拠点の種類と今のランクまでのもののうち、まだ持っていないもの（全部持っていればどれか）を1つ渡して、訪問を記録する |
| `openTaneGarden` | なし | 箱庭と所持しているものを返す |
| `saveTaneGarden` | 配置の配列 | 存在するものか・マスの範囲内か・1マス1個か・所持数を超えていないかを確かめて、本人の箱庭だけを書き換える |

Lambda は2本に分ける: 拠点（`chizu-tane-base`: start / place / check-in）と箱庭（`chizu-tane-garden`: open / save）。拠点の方は geojson を読むので、メモリとタイムアウトを多めにする。

## 9. 開発・テスト用の位置指定

位置情報のゲームは、机の前では試せない。開発中と dev 環境では、位置を手で指定できるようにする。

- 「いまいる地区」の画面で、地図をタップした場所を現在地として使う（市区町村を選ぶのは地図パズルの `MapAreaSelector` を流用）
- 有効にするのは dev 環境（devgame.usapo.net）と手元（localhost）だけ。本番のビルドでは出さない
- dev の Lambda では速さの確認をしない（指定した場所へ一瞬で移れるように）。本番の Lambda では確かめる。ブランチ名で切り替える
- 位置を手で指定できるのは、ブラウザの位置情報を偽るのと同じこと。本番でもブラウザの開発ツールを使えば偽れるので、これで守りが弱くなるわけではない（全体設計書 12章）

## 10. 画像素材

### 10.1 試作の進め方

- コードは仮の素材（手で描いた SVG。64×64、下端の中央が地面に接する点、光は左上から）で進める。試作で使うのは5種類だけなので、AI 素材ができたら画像のパスを差し替える
- **AI 素材の検討はコードと別に並行して進める**。絵柄を決めて、まず各コースのランク1〜2あたりから8個ほど作り、箱庭のマス目の画像の上に並べて見比べる。気に入った絵柄ができたら、試作の5種類から差し替える

### 10.2 絵柄の方向

- かわいらしいミニチュア風、またはローポリ風（試して決める）
- 柔らかな色合い、斜め上から見た視点、シンプルで見分けやすい形
- 背景を透過した PNG。ファイル名はアイテムID

### 10.3 素材ごとの確認

- 背景が透過されているか、輪郭がはっきりしているか
- 縮小しても見分けられるか（箱庭の1マスはスマホで 30px 前後、集めたものの一覧ではもう少し大きい）
- 視点と影の向きが他の素材とそろっているか
- 縦横比や余白が極端に違わないか
- 必要なら切り抜き・大きさの調整をする

## 11. 評価の観点

試作ができたら、dev 環境で実際に歩いて次を確かめる。結果を見て、全体設計書のフェーズ4以降（成長・ランクアップ・レベル）に進むかを決める。

1. 拠点を置く → 別の地区でチェックインする、の流れが説明なしで分かるか
2. 「他の人のタネに行ってみたい」と思えるか。もらえたときにうれしいか
3. 地区の判定は実用になるか（誤差で違う地区になる頻度、境界付近、建物の中）
4. 集めたものの一覧・タネニワが、ご褒美として効いているか。違うコースのものを混ぜても違和感がないか
5. スマホで操作しやすいか（位置情報の許可、地図、マス目の大きさ）
6. 費用と運用の手間が増えすぎないか（Lambda での geojson の読み込み、DynamoDB）

## 12. 作る順番

メインの「訪ねてもらう」を先に作り、おまけの箱庭は最後にする。

| 順 | 内容 | できたと言える状態 |
|---|---|---|
| 1 | コースの表とアイテムの定義・仮素材・コース選び | コースを選ぶと、最初のものを3つ持った状態で始まる |
| 2 | いまいる地区（位置情報 → 市区町村 → 町丁の判定 → 地図）と開発用の位置指定 | スマホで現在地の地区名が出る。dev では地図のタップで場所を指定できる |
| 3 | 拠点を置く | 地区にタネをまけ、同じ地区には他の人が開けない |
| 4 | チェックインと集めたもの | 他の人のタネからもらえ、同じ日にもう一度はもらえない。集めたものの一覧に出る |
| 5 | タネニワ（おまけ） | 持っているものを並べて保存し、開き直しても同じ状態で出る |
| 6 | dev 環境で2アカウントを使って一周を試す | 11章の観点で評価できる |

## 13. 未決事項

- 箱庭の広さ（10×10）がスマホで操作しやすいか（試して決める）
- URL・モデル名・フォルダ名のローマ字（本書では `chizu-tane`・`GameTane*`・`chizuTane` とした）
